## Global Constraints

- **Форма дня — как в неделе 2** (её Global Constraints действуют целиком):
  - 2–3 мысли с `bookRef`;
  - схем ≥1, только из текста книги. Нельзя: `ch7_release`, `ch11_design`, `ch8_reviewsplit`, `ch8_maint`, `ch8_review`;
  - ровно один тренажёр или ситуация;
  - ИИ `ask`;
  - тест на 5–7 вопросов;
  - 4–8 новых карточек;
  - `minutes {20, 100}`;
  - 4–7 шагов практики и последним — «Обновить наставника и проверить день»;
  - запрос ≤ 400 знаков, `done` ≤ 120.
- **Большой части тем недели в книге нет** (§0 п. 3): питание, бета, Storage, политика конфиденциальности, service worker, удаление пользователя Auth. Такие места подписываются «В курсе: …» или отдаются агенту на сверку с документацией. Фактом не утверждаются.
- **Две честные подмены** (§0 п. 4):
  - `s16` — про обратную связь модели; для людей опора — `s32`;
  - «не юридическая консультация» в `s57` сказано об интеллектуальной собственности, не о политике.
- **Миграции:**
  - «следующим номером» с постоянным суффиксом: `_nutrition`, `_measurements`, `_photos`, `_client_key`, `_coach_invites`, `_feedback`, `_errors`, `_delete_account`;
  - RLS — в той же миграции;
  - выпуск всех миграций дня по порядку: разработка после «да» → SQL Editor продакшна (ученик) → `git push`.
- **Каждое право, которое проверяет тест, названо в запросе миграции.** Негативный тест проверяет настоящий обход от чужого и от нового пользователя.
- **Тесты с базой:**
  - ключ публичный, секретный не брать;
  - строки убирать по своим id в `afterAll` и проверять, что их нет;
  - если RLS не даёт удалить — стоп, политики не менять.
- **e2e убирает за собой.**
- **Данные беты** (дни 19–20) — чужие люди и их здоровье. Они живут только в продакшне. Агент туда не ходит. Замечания и журнал ученик читает сам и передаёт агенту пересказ без имён и данных о здоровье (s19, s60, s40).
- **Журнал ошибок** — по правилу дня 14: id, время, действие, код ошибки. Без текста ошибки базы, без кодов приглашений из адреса (`/join/<код>` обрезать).
- **Удаление аккаунта** (день 21) — без секретного ключа:
  - порядок: файлы Storage сессией пользователя → функция базы удаляет строки и пользователя → выход;
  - как именно удалить пользователя Auth — агент сверяется с документацией Supabase;
  - цену частичного сбоя назвать.
- **Свой домен — по желанию** (s81). Строку недели в `content/weeks.json` «запуск на своём домене» поправить в Задаче 1.
- Остальное — как в неделе 2: ветка, коммиты с двумя строками атрибуции, `build:graph` и `build:mentor`, проверки.

## Review Focus

1. **Бета и чужие данные.** В продакшн ходит только ученик, агенту — пересказ без имён. Тестеры приходят по тренерскому приглашению, и тренер создаёт приглашения только своим подопечным.
2. **Фото (день 17).** Бакет приватный. Политики на `storage.objects` пускают по первой папке пути. Тренер читает только своих. Ссылки подписанные и с коротким сроком. Удаление — через Storage API.
3. **Очередь без сети (день 18).** Ключ — id вошедшего. Повтор не создаёт дубль: уникальный `client_key`, тот же ответ. Выход и чужой телефон не уносят чужие подходы.
4. **Удаление аккаунта и политика (день 21).** Без секретного ключа, порядок шагов назван. Политика не утверждает законов фактом и честно говорит о копиях.
5. **Итоговый тест курса.** 12 вопросов по всему курсу: по 4 на неделю. Позиции ответов 3/3/3/3. Ключ `week-3`, заголовок «Итоговый тест курса».
