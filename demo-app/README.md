# demo-app — приложение тренера для видеоуроков

Здесь живёт приложение тренера, на котором показаны примеры в видеоуроках курса. Это не отдельный проект для разработки, а источник записей: каждая команда, её вывод, дифф и коммит в ролике взяты из настоящей работы над этим приложением.

- `sessions/` — шаги сессий работы над приложением, по одной сессии в файле (`s01-start.mjs`, `s02-sets.mjs`, …). Сессии идут цепочкой: каждая продолжает предыдущую (поле `from`).
- `app/` — исходники приложения в том виде, в каком их оставила последняя сессия (файлы из `git ls-files` после записи). Если сессия кончается переключением ветки (`s05-proto` возвращается на `main`), это дерево той ветки, где проект стоит в конце, а не последнего коммита записи.
- `state/` — состояния проекта после каждой сессии, по архиву на сессию (`s01-start.tar.gz`, …): с них можно продолжить запись с середины цепочки.
- Записи сессий — `course/video/sessions/<id>.json`, их проигрывают ролики.

## Сессии

Двенадцать сессий недели 1 (`s01-start` … `s12-agent`) и сессии недели 2 (с `s13-feedback`), по строке на сессию. Дата — поле `date` сессии (московское время): от него идут даты коммитов записи. «База» — `db: true` (раздел «Локальная база вместо Supabase»). Ролики — уроки `course/video/lessons/*`, которые берут эту запись.

## Правило: правится только записью

`app/`, `state/` и записи `course/video/sessions/*.json` руками не правятся никогда. Если нужно другое приложение или другой вывод, меняются шаги в `sessions/*.mjs`, и цепочка записывается заново: вся или с нужной сессии (следующий раздел).

## Как перезаписать

Из папки `course/`:

```sh
node scripts/record-session.mjs
```

Рекордер по-настоящему проигрывает все сессии по порядку во временной папке: создаёт проект через `create-next-app`, ставит пакеты (кэш npm — `course/node_modules/.cache/session-npm`), выполняет команды и коммиты, запускает `npm run dev` и открывает страницу в Chromium. Запись идёт несколько минут. В конце рекордер пишет `course/video/sessions/<id>.json` и заменяет `app/`. Команды идут как в терминале человека: без `NODE_ENV`, `NODE_OPTIONS`, меток тестов (`VITEST*`, `TEST`, `JEST_WORKER_ID`), меток ИИ-агента, `GIT_*` и настроек подключения к базе (`PG*`, `DATABASE_URL`) из окружения запуска — например, при `NODE_ENV=test` или `production` `next dev` дописывает в `tsconfig.json` лишнее, а `npm ci` при `production` не ставит devDependencies.

После перезаписи — проверка записей:

```sh
npx vitest run video/sessions
```

Полная перезапись в другой день может дать другие записи. У зависимостей, которые ставит `create-next-app`, версии записаны диапазонами `^` (`"eslint": "^9"`, `"tailwindcss": "^4"` …), поэтому npm возьмёт самые свежие подходящие версии: изменятся `package-lock.json`, хеши коммитов и строки вывода (число пакетов, предупреждения, время). Уроки ссылаются на id событий и диапазоны строк вывода, поэтому после перезаписи прогоните и тесты уроков — весь `npm test`.

## Запись с середины цепочки

Зачем. У зависимостей версии записаны диапазонами `^`, поэтому полная перезапись в другой день даёт другие версии пакетов, другие `package-lock.json` и хеши коммитов, и всё, что записано раньше, расходится с роликами. Новая сессия (`s13-…`, `s14-…` — после `s12-agent`, последней записи недели 1) должна дописываться к цепочке, не меняя прежние записи. Для этого рекордер после каждой сессии сохраняет её состояние, а записывает новые сессии от него.

Состояние сессии — архив (`tar -czf`) папки проекта `trainer-app` на конец сессии: с `.git` и игнорируемыми файлами вроде `.env.local`, но без `node_modules`, `.next`, `test-results` и `playwright-report`. Лежит в `state/<id>.tar.gz`. Больше ничего из временной папки записи (домашняя папка `~` вне проекта, кэш) в состояние не входит: сессии, которые продолжают с состояния, не должны от него зависеть. При восстановлении проект разворачивается из архива, а если в нём есть `package-lock.json`, пакеты ставятся `npm ci --prefer-offline --no-audit --no-fund` — ровно те версии, что были в записи (в запись эта команда не попадает).

Из папки `course/`:

```sh
node scripts/record-session.mjs --from <id>
```

Записывает сессию `<id>` и все следующие от состояния сессии, которая идёт перед ней. Записи и состояния сессий раньше `<id>` не трогаются, `app/` заменяется (он всегда соответствует последней сессии). `--from` первой сессии цепочки — то же, что запись всей цепочки.

- Новая сессия `s13-…` (`from: 's12-agent'`) пишется с `--from s13-…`: от состояния `s12-agent`, записи `s01-start` … `s12-agent` остаются как есть.
- `--from s06-auth` перепишет `s06-auth` и все сессии после неё (`s07-cycle` … `s12-agent`) от состояния `s05-proto`: у коммитов этих сессий могут смениться хеши, а у вывода — строки, поэтому потом нужен весь `npm test`.

- Состояния создаёт полная запись (`node scripts/record-session.mjs` без аргументов): она сохраняет состояния всех сессий. После полной перезаписи состояния и записи заменяются вместе, и коммитить их нужно вместе.
- Нет архива нужной сессии — ошибка «Нет состояния сессии «…» (demo-app/state/….tar.gz): запишите цепочку целиком». Неизвестный id — ошибка со списком сессий цепочки.
- Записи и состояния заменяются только после того, как вся запись прошла и проект совпал с коммитом HEAD (то есть без правок после коммита): сорванная запись ничего не портит.
- Запись с середины даёт те же хеши коммитов и те же записи, что полная запись из тех же состояний, если команды сессий не зависят от `node_modules` и других файлов, которых нет в состоянии, пока их не поставили.
- Папки можно подменить переменными окружения `RECORD_SESSIONS_DIR`, `RECORD_OUT_DIR`, `RECORD_APP_DIR`, `RECORD_STATE_DIR` (по умолчанию `demo-app/sessions`, `course/video/sessions`, `demo-app/app`, `demo-app/state`); так рекордер проверяют тесты.

## Локальная база вместо Supabase

Docker в контейнере записи не запускается, поэтому `supabase start` недоступен. Сессия с полем `db: true` (рядом с `id`, `from`, `date`) получает замену: обычный PostgreSQL 16 из `/usr/lib/postgresql/16/bin` на порту 54322 — это порт базы `supabase start`.

Перед первым шагом такой сессии рекордер:

1. создаёт во временной папке системы папку `rec-pg-…` и отдаёт её пользователю `postgres` (Postgres не запускается от root);
2. создаёт кластер (`initdb`: UTF8, `C.UTF-8`, вход без пароля) и запускает сервер на `127.0.0.1:54322` — обе команды через `runuser -u postgres`;
3. выполняет `course/scripts/session/supabase-local.sql`, затем файлы проекта `supabase/migrations/*.sql` по имени и `supabase/seed.sql`, если они есть, — как `supabase db reset`. Их вывод в запись не попадает; ошибка SQL останавливает запись с текстом ошибки и именем файла;
4. добавляет в окружение команд сессии `PGHOST=127.0.0.1`, `PGPORT=54322`, `PGUSER=postgres`, `PGDATABASE=postgres` и `DATABASE_URL=postgresql://postgres@127.0.0.1:54322/postgres`: `psql` и приложение подключаются без настроек. У сессий без `db` этих переменных нет, и чужие `PG*` и `DATABASE_URL` из окружения запуска не попадают ни в какие команды.

В конце сессии, при ошибке шага и при выходе рекордера (Ctrl+C, kill, обрыв терминала или ssh) сервер останавливается (`pg_ctl stop -m fast`), а папка удаляется. Каждая сессия с `db: true` начинает с чистой базы, собранной из миграций и seed, которые лежат в проекте на начало сессии: строки, добавленные командами предыдущей сессии, в следующую не переходят. Новую миграцию внутри сессии применяют шагом `run` (`psql -f supabase/migrations/0002_….sql`). Тесты уроков базу не запускают — только тесты самого рекордера. Если рекордер убит без возможности выйти штатно (`kill -9`, нехватка памяти), Postgres остаётся работать. Вручную убирать его не нужно: перед запуском новой базы рекордер находит папки `rec-pg-…` в `tmpdir()` с работающим сервером, останавливает его и удаляет папку. Ошибка «Address already in use» в тексте ошибки значит, что порт 54322 занят чем-то другим (не остатком рекордера).

Что повторяет слой `supabase-local.sql` из Supabase:

- схему `extensions` с расширением `pgcrypto`, как в Supabase: `extensions.crypt()`, `extensions.gen_salt()` и `create extension … with schema extensions` в миграциях (например, `uuid-ossp`) работают. Схема есть в `search_path` базы (`"$user", public, extensions`), поэтому `crypt()` и `gen_salt()` вызываются и без имени схемы; ролям `anon`, `authenticated`, `service_role` на схему выдан `usage`;
- роли `anon` и `authenticated` (без входа) и `service_role` (без входа, обходит RLS);
- права этих ролей на схему `public` и права по умолчанию на таблицы, последовательности и функции, которые создают миграции;
- схему `auth` с таблицей `auth.users (id, email, encrypted_password, created_at)` — в настоящем Supabase столбцов больше;
- функции `auth.uid()` и `auth.role()`: они читают `request.jwt.claims`, поэтому политики RLS можно проверять так: `select set_config('request.jwt.claims', '{"sub":"…","role":"authenticated"}', false)`, затем `set role authenticated`.

Чего слой не повторяет: нет PostgREST (нет HTTP-интерфейса `/rest/v1`, `supabase-js` не подключить — приложение ходит в базу напрямую по `DATABASE_URL`), нет настоящего Auth (токенов, писем, провайдеров входа, `supabase.auth.*`): вход в приложении — свой маршрут, который проверяет пароль через `crypt()` по `auth.users`. Нет и хранилища файлов, Realtime и служебных ролей Supabase (`authenticator`, `supabase_admin`…). SQL миграций пишется таким, какой принял бы Supabase. В роликах это сказано честно: когда кадр показывает базу, на доске подпись «локальная база вместо Supabase».

## Что нужно на машине

- Свободный порт 3000: на нём работает `npm run dev` сессии. Тест рекордера (`scripts/session/record.test.ts`) и `npm test` тоже поднимают сервер на этом порту. Рекордер, убитый без возможности выйти штатно (`kill -9`, нехватка памяти), оставляет `npm run dev` работать: сервер живёт в своей группе процессов. Postgres такой записи следующая запись убирает сама (раздел выше), а сервер — нет: `next dev` при занятом порте может уйти на 3001 (`Port 3000 is in use…`) и всё равно написать `Ready` (или упасть сразу — если `PORT` задан явно), а шаги `browser` идут на `localhost:3000` — на старый сервер со старым кодом. Поэтому перед командой с `until` рекордер проверяет, что к порту 3000 не подключиться, и иначе останавливает запись до запуска команды: «Сессия «…», шаг «dev»: порт 3000 занят (остаток прошлой записи?) — остановите процесс и запустите снова». Чужие процессы рекордер не останавливает: найдите процесс на порту (`lsof -i :3000`), остановите его сами и запустите запись снова.
- Для сессий с `db: true` — свободный порт 54322, PostgreSQL 16 в `/usr/lib/postgresql/16/bin` (`initdb`, `pg_ctl`, `postgres`) с расширением `pgcrypto`, `psql` в `PATH`, пользователь `postgres` и `runuser`. Рекордер должен быть запущен от root; иначе ошибка «Сессия с db: true: Postgres запускается от пользователя postgres, рекордер нужно запускать от root (сессия «…»)» — до запуска первой команды и только для сессий, которые будут проиграны (при `--from` сессии раньше не считаются). Тесты рекордера в `npm test` тоже поднимают базу на этом порту.
- Chromium из `/opt/pw-browsers`: Playwright берёт его оттуда, когда в окружении задана переменная `PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers` (в контейнере записи она задана; без неё Playwright ищет браузер в своей папке по умолчанию, `~/.cache/ms-playwright`). `playwright install` не запускать.
- Доступ к реестру npm: пакеты Next.js ставятся из сети (при записи с середины — `npm ci` по `package-lock.json` из состояния, быстрее, если пакеты уже в кэше).
- `tar` и `git` в `PATH`.
